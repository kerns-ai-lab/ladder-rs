# Data Architecture

**ladder-rs Platform**
**Date:** 2026-04-15

---

## Overview

The ladder-rs platform uses a single SQLite database in WAL mode as its sole persistence layer. All tables are owned and managed by the `ladder-rs-persistence` crate via sqlx migrations. No other process may modify the schema directly.

This document defines the complete schema: tables, columns, types, indexes, and foreign key relationships. SQL is written for SQLite but uses standard syntax portable to PostgreSQL (per NFR-PORT-001). PostgreSQL-incompatible SQLite syntax is noted where used.

---

## Database Configuration

Applied at connection pool initialization via `PRAGMA` statements:

```sql
PRAGMA journal_mode = WAL;
-- WAL mode: one writer + multiple concurrent readers without lock escalation.
-- Required for concurrent access by both the Axum backend and the Swarm Operator process.

PRAGMA busy_timeout = 5000;
-- 5-second timeout before returning SQLITE_BUSY.
-- Configurable via environment variable at deployment time.
-- Prevents immediate failure when a write is contended between the two processes.

PRAGMA foreign_keys = ON;
-- SQLite disables FK enforcement by default. Explicitly enabled.

PRAGMA synchronous = NORMAL;
-- Safe with WAL mode. FULL synchronous provides no additional crash safety
-- in WAL mode but adds significant write latency.
```

## Schema

### Authentication and User Management

#### `users`

Stores all platform user accounts. The global `role` column encodes the three-role model.

```sql
CREATE TABLE users (
    id                    INTEGER PRIMARY KEY AUTOINCREMENT,
    username              TEXT NOT NULL UNIQUE,
    email                 TEXT NOT NULL UNIQUE,
    password_hash         TEXT NOT NULL,           -- argon2id hash
    role                  TEXT NOT NULL DEFAULT 'viewer'
                              CHECK (role IN ('admin', 'operator', 'viewer')),
    is_active             INTEGER NOT NULL DEFAULT 1,   -- 0 = soft-deactivated
    force_password_change INTEGER NOT NULL DEFAULT 0,   -- 1 = must change on next login
    created_at            TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now'))
);

CREATE INDEX idx_users_username ON users (username);
CREATE INDEX idx_users_email    ON users (email);
```

**Notes:**
- `role = 'admin'` is the global Admin. Only one admin record is expected (bootstrap produces the first; additional admin accounts are an admin-only operation).
- `role = 'operator'` is the global League Operator role marker. Actual league scope is encoded in `league_operators`.
- `role = 'viewer'` is the default for Player/Viewer accounts.
- `force_password_change = 1` blocks all API access except `POST /api/auth/change-password`.

#### `login_attempts`

Tracks every login attempt for rate limiting. Lockout state is derived from this table — no separate lockout table.

```sql
CREATE TABLE login_attempts (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id      INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    attempted_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now')),
    success      INTEGER NOT NULL     -- 1 = success, 0 = failure
);

CREATE INDEX idx_login_attempts_user_time ON login_attempts (user_id, attempted_at DESC);
```

**Lockout query (consecutive failures):** Counts failed attempts since the most recent success. A successful login resets the counter to zero — only unbroken consecutive failures trigger the lockout. This matches NFR-SEC-001 exactly.

```sql
SELECT COUNT(*) FROM login_attempts
WHERE user_id = ?
  AND success = 0
  AND id > (
    SELECT COALESCE(MAX(id), 0)
    FROM login_attempts
    WHERE user_id = ? AND success = 1
  )
```

If the count is >= 10, the account is locked. The lockout lifts automatically once the 15-minute window from the 10th failure expires (checked against `attempted_at` of the 10th failure row).

**Retention:** Old records do not need explicit cleanup for v1 correctness. A background sweep of records older than 24 hours is a future optimization.

#### `sessions`

Managed by `tower-sessions-sqlx-store`. Format is dictated by the tower-sessions library. Shown here for schema completeness.

```sql
CREATE TABLE sessions (
    id         TEXT PRIMARY KEY,        -- cryptographically random session ID
    data       BLOB NOT NULL,           -- serialized session data (tower-sessions internal)
    expires_at TEXT NOT NULL
);

CREATE INDEX idx_sessions_expires ON sessions (expires_at);
```

**Notes:** The backend does not query this table directly — all access goes through the `tower-sessions` API. The `expires_at` index supports background expiry sweeps by the tower-sessions library.

#### `invite_tokens`

Invite links generated by Admin or League Operators for player-to-account linking.

```sql
CREATE TABLE invite_tokens (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    player_id   INTEGER NOT NULL REFERENCES players(id) ON DELETE CASCADE,
    token_hash  TEXT NOT NULL UNIQUE,  -- SHA-256 of the plaintext token
    expires_at  TEXT NOT NULL,         -- token lifetime: 7 days from created_at
    claimed_at  TEXT,                  -- NULL = unclaimed; set when user claims
    claimed_by  INTEGER REFERENCES users(id),
    created_by  INTEGER NOT NULL REFERENCES users(id),
    created_at  TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now'))
);

CREATE INDEX idx_invite_tokens_hash    ON invite_tokens (token_hash);
CREATE INDEX idx_invite_tokens_player  ON invite_tokens (player_id);
```

**Token lifecycle:** The plaintext token is returned to the creator exactly once at creation time. The hash is stored. `claimed_at` being non-NULL means the token has been used and cannot be claimed again.

**Registration use:** When a new user registers via `POST /api/auth/register`, the `invite_token` field in the request body is validated and claimed atomically with account creation. The token links the new user account to the player record in a single transaction (ADR-0008).

#### `api_keys`

Library API keys for swarm operator authentication. Each key is associated with a `user_id` that has operator role and league assignments. Used to initialize `SwarmContext` in the `ladder-rs-persistence` crate (ADR-0009).

```sql
CREATE TABLE api_keys (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    key_hash    TEXT NOT NULL UNIQUE,   -- SHA-256 of the plaintext key
    user_id     INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    description TEXT NOT NULL,
    created_by  INTEGER NOT NULL REFERENCES users(id),
    created_at  TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now'))
);

CREATE INDEX idx_api_keys_user ON api_keys (user_id);
```

**Key lifecycle:** Admin generates a key via `POST /api/admin/api-keys`. The plaintext 32-byte random key is returned exactly once. The swarm operator embeds the key in their process environment. Revocation via `DELETE /api/admin/api-keys/:id` — the row deletion prevents future initializations; the running process is unaffected until restart. No automatic expiry in v1.

### League and Season Management

#### `leagues`

```sql
CREATE TABLE leagues (
    id                          INTEGER PRIMARY KEY AUTOINCREMENT,
    name                        TEXT NOT NULL,
    description                 TEXT NOT NULL DEFAULT '',
    status                      TEXT NOT NULL DEFAULT 'active'
                                    CHECK (status IN ('active', 'archived')),
    visibility                  TEXT NOT NULL DEFAULT 'public'
                                    CHECK (visibility IN ('public', 'private')),
    active_agent_threshold_days INTEGER NOT NULL DEFAULT 30,  -- configurable per-league (SR-SW-001)
    created_at                  TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now')),
    created_by                  INTEGER NOT NULL REFERENCES users(id)
);

CREATE INDEX idx_leagues_status     ON leagues (status);
CREATE INDEX idx_leagues_visibility ON leagues (visibility);
```

#### `league_operators`

Maps users to the leagues they operate. A user with `role = 'operator'` in `users` may be an operator for zero or more leagues.

```sql
CREATE TABLE league_operators (
    league_id  INTEGER NOT NULL REFERENCES leagues(id) ON DELETE CASCADE,
    user_id    INTEGER NOT NULL REFERENCES users(id)   ON DELETE CASCADE,
    granted_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now')),
    granted_by INTEGER NOT NULL REFERENCES users(id),
    PRIMARY KEY (league_id, user_id)
);

CREATE INDEX idx_league_operators_user ON league_operators (user_id);
```

#### `seasons`

One row per season within a league. The current open season has `end_date IS NULL`.

```sql
CREATE TABLE seasons (
    id               INTEGER PRIMARY KEY AUTOINCREMENT,
    league_id        INTEGER NOT NULL REFERENCES leagues(id) ON DELETE CASCADE,
    algorithm        TEXT NOT NULL CHECK (algorithm IN ('elo', 'glicko2', 'trueskill')),
    algorithm_params TEXT NOT NULL,  -- JSON: algorithm-specific parameters
    seeding_choice   TEXT NOT NULL DEFAULT 'reset'
                         CHECK (seeding_choice IN ('reset', 'ordinal')),
    start_date       TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now')),
    end_date         TEXT              -- NULL = season is open
);

CREATE INDEX idx_seasons_league     ON seasons (league_id);
CREATE INDEX idx_seasons_league_end ON seasons (league_id, end_date);
```

**`algorithm_params` JSON examples:**
- Elo: `{"k_factor": 32, "initial_rating": 1000}`
- Glicko-2: `{"initial_mu": 1500, "initial_rd": 350, "initial_volatility": 0.06, "tau": 0.5}`
- TrueSkill: `{"initial_mu": 25.0, "initial_sigma": 8.333, "beta": 4.167, "tau": 0.0833, "draw_probability": 0.1}`

### Player Management

#### `players`

Global player table. Players exist independently of leagues — they join leagues via `league_players`.

```sql
CREATE TABLE players (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    name        TEXT NOT NULL UNIQUE,         -- globally unique canonical identifier
    nickname    TEXT,                         -- optional display name; no uniqueness constraint
    player_type TEXT NOT NULL DEFAULT 'human'
                    CHECK (player_type IN ('human', 'non-human')),
    is_active   INTEGER NOT NULL DEFAULT 1,  -- global soft-delete flag
    created_at  TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now'))
);

CREATE UNIQUE INDEX idx_players_name       ON players (name COLLATE NOCASE);
CREATE        INDEX idx_players_name_prefix ON players (name COLLATE NOCASE);
-- name is globally unique (case-insensitive). get_or_create_player lookup is unambiguous.
-- nickname has no index — it is display-only and searched in combination with name.
```

**Display rule:** All UI surfaces show `nickname ?? name` — nickname when set, canonical name as fallback. Search results and autocomplete show nickname when available. `get_or_create_player` always uses `name` for unambiguous lookup.

#### `player_account_links`

Records the result of claiming an invite token — the association between a user account and a player record.

```sql
CREATE TABLE player_account_links (
    player_id  INTEGER NOT NULL REFERENCES players(id) ON DELETE CASCADE,
    user_id    INTEGER NOT NULL REFERENCES users(id)   ON DELETE CASCADE,
    created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now')),
    created_by INTEGER NOT NULL REFERENCES users(id),
    PRIMARY KEY (player_id, user_id)
);

CREATE INDEX idx_player_account_links_user ON player_account_links (user_id);
```

#### `league_players`

Tracks which players are in which leagues, including per-league active status.

```sql
CREATE TABLE league_players (
    league_id  INTEGER NOT NULL REFERENCES leagues(id)  ON DELETE CASCADE,
    player_id  INTEGER NOT NULL REFERENCES players(id)  ON DELETE CASCADE,
    joined_at  TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now')),
    is_active  INTEGER NOT NULL DEFAULT 1,  -- soft-delete: 0 = removed from league
    PRIMARY KEY (league_id, player_id)
);

CREATE INDEX idx_league_players_player    ON league_players (player_id);
CREATE INDEX idx_league_players_active    ON league_players (league_id, is_active);
```

#### `player_aliases`

Bi-directional alias link between two player records. Both the primary and alias records persist; the link tells the system to treat them as one player for rating purposes.

```sql
CREATE TABLE player_aliases (
    primary_player_id INTEGER NOT NULL REFERENCES players(id) ON DELETE CASCADE,
    alias_player_id   INTEGER NOT NULL REFERENCES players(id) ON DELETE CASCADE,
    created_at        TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now')),
    created_by        INTEGER NOT NULL REFERENCES users(id),
    PRIMARY KEY (primary_player_id, alias_player_id),
    CHECK (primary_player_id <> alias_player_id)
);

CREATE INDEX idx_player_aliases_alias   ON player_aliases (alias_player_id);
CREATE INDEX idx_player_aliases_primary ON player_aliases (primary_player_id);
```

### Match Recording

#### `matches`

One row per match event.

```sql
CREATE TABLE matches (
    id                  INTEGER PRIMARY KEY AUTOINCREMENT,
    season_id           INTEGER NOT NULL REFERENCES seasons(id) ON DELETE RESTRICT,
    recorded_at         TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now')),
    convergence_quality TEXT NOT NULL DEFAULT 'converged'
                            CHECK (convergence_quality IN ('converged', 'degraded')),
    score_metadata      TEXT,  -- JSON, optional display-only score data
    is_corrected        INTEGER NOT NULL DEFAULT 0   -- 1 = admin correction applied
);

CREATE INDEX idx_matches_season          ON matches (season_id);
CREATE INDEX idx_matches_season_time     ON matches (season_id, recorded_at);
CREATE INDEX idx_matches_recorded_at     ON matches (recorded_at);
```

**ON DELETE RESTRICT on season_id:** Matches cannot exist without a season. Deleting a season requires deleting matches first (admin-only edge case).

#### `match_participants`

One row per player per match. `placement` is 1-based (1 = winner in 1v1; 1 = first place in N-player).

```sql
CREATE TABLE match_participants (
    match_id   INTEGER NOT NULL REFERENCES matches(id) ON DELETE CASCADE,
    player_id  INTEGER NOT NULL REFERENCES players(id) ON DELETE RESTRICT,
    placement  INTEGER NOT NULL,   -- 1 = winner / first place
    is_draw    INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY (match_id, player_id)
);

CREATE INDEX idx_match_participants_player ON match_participants (player_id);
CREATE INDEX idx_match_participants_match  ON match_participants (match_id);
```

#### `match_audit_log`

Records admin corrections. One row per correction event.

```sql
CREATE TABLE match_audit_log (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    match_id     INTEGER NOT NULL REFERENCES matches(id) ON DELETE CASCADE,
    changed_by   INTEGER NOT NULL REFERENCES users(id),
    changed_at   TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now')),
    before_state TEXT NOT NULL,  -- JSON snapshot of match + participants before change
    after_state  TEXT NOT NULL   -- JSON snapshot of match + participants after change
);

CREATE INDEX idx_audit_log_match ON match_audit_log (match_id);
```

### Rating Data

#### `rating_snapshots`

One row per player per match in the season. Represents the player's rating state immediately after the match was processed. This is the primary source for leaderboards and rating history charts.

```sql
CREATE TABLE rating_snapshots (
    id                  INTEGER PRIMARY KEY AUTOINCREMENT,
    match_id            INTEGER NOT NULL REFERENCES matches(id)  ON DELETE CASCADE,
    player_id           INTEGER NOT NULL REFERENCES players(id)  ON DELETE RESTRICT,
    season_id           INTEGER NOT NULL REFERENCES seasons(id)  ON DELETE RESTRICT,
    rating              REAL NOT NULL,        -- mu (all algorithms)
    deviation           REAL,                 -- RD (Glicko-2 only; NULL for Elo/TrueSkill)
    uncertainty         REAL,                 -- sigma (TrueSkill only; NULL for Elo/Glicko-2)
    conservative_rating REAL NOT NULL,        -- pre-computed sort key (see SR-ALG-005)
    timestamp           TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now'))
);

-- Leaderboard query: latest snapshot per player in a season, ordered by conservative_rating
CREATE INDEX idx_rating_snapshots_season_player_match
    ON rating_snapshots (season_id, player_id, match_id DESC);

-- Rating history chart: all snapshots for a player in a season, ordered chronologically
CREATE INDEX idx_rating_snapshots_player_season_time
    ON rating_snapshots (player_id, season_id, timestamp);

-- Season overview: final snapshot per player across all seasons
CREATE INDEX idx_rating_snapshots_player_match
    ON rating_snapshots (player_id, match_id DESC);
```

**Leaderboard query pattern:** To get the current leaderboard for a season, the query retrieves the maximum `match_id` snapshot per player (the most recent), then sorts by `conservative_rating DESC`. Because `conservative_rating` is pre-computed and indexed, this avoids per-query arithmetic over potentially millions of rows.

**`conservative_rating` values:**
- Elo: `rating` (no uncertainty)
- Glicko-2: `rating - 2 * deviation`
- TrueSkill: `rating - 3 * uncertainty`

### Background Jobs

#### `recalculation_jobs`

One row per queued, running, or completed recalculation job.

```sql
CREATE TABLE recalculation_jobs (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    season_id    INTEGER NOT NULL REFERENCES seasons(id) ON DELETE CASCADE,
    status       TEXT NOT NULL DEFAULT 'queued'
                     CHECK (status IN ('queued', 'in_progress', 'completed', 'failed')),
    triggered_by INTEGER NOT NULL REFERENCES users(id),
    triggered_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now')),
    started_at   TEXT,        -- NULL until claimed by the poller
    completed_at TEXT,        -- NULL until finished
    error_message TEXT        -- NULL on success; populated on failure
);

CREATE INDEX idx_recalc_jobs_status        ON recalculation_jobs (status);
CREATE INDEX idx_recalc_jobs_season_status ON recalculation_jobs (season_id, status);
```

**Claim query (atomic, see Job Repository component):**

```sql
UPDATE recalculation_jobs
SET status = 'in_progress', started_at = strftime('%Y-%m-%dT%H:%M:%SZ', 'now')
WHERE id = (
    SELECT id FROM recalculation_jobs
    WHERE status = 'queued'
    ORDER BY triggered_at ASC
    LIMIT 1
)
RETURNING *;
```

## Entity Relationship Summary

```
users
  ├── has many login_attempts
  ├── has many sessions (via tower-sessions)
  ├── has many invite_tokens (created_by)
  ├── has many league_operators (granted to leagues)
  └── has many player_account_links (linked to player records)

leagues
  ├── has many league_operators (users assigned to operate)
  ├── has many seasons
  └── has many league_players (players in league)

seasons
  ├── belongs to league
  ├── has many matches
  └── has many recalculation_jobs

players
  ├── has many league_players (league memberships)
  ├── has many match_participants
  ├── has many rating_snapshots
  ├── has many player_aliases (as primary or alias)
  └── has at most one player_account_link

matches
  ├── belongs to season
  ├── has many match_participants
  ├── has many rating_snapshots
  └── has many match_audit_log entries (admin corrections)

match_participants
  ├── belongs to match
  └── belongs to player

rating_snapshots
  ├── belongs to match
  ├── belongs to player
  └── belongs to season
```

## Index Strategy Rationale

The two highest-load query patterns at scale (10,000 players, 1M matches) are:

### Leaderboard at Scale

Query: "Get current ranking for all active players in season X."

Naive approach: `SELECT player_id, MAX(match_id) as last_match FROM rating_snapshots WHERE season_id = X GROUP BY player_id`. At 1M matches and 10K players, this requires a full season scan.

Optimized approach enabled by `idx_rating_snapshots_season_player_match`:
- SQLite can use this index to find the last `match_id` per `(season_id, player_id)` without a full table scan
- The pre-computed `conservative_rating` column on each row eliminates per-query arithmetic
- Target: < 500ms for 10K players per NFR-PERF-002

### Player Search Autocomplete

Query: "Find players whose name starts with 'Alp'."

The `idx_players_name_prefix` index with `COLLATE NOCASE` enables efficient B-tree prefix scans for `WHERE name LIKE 'Alp%' COLLATE NOCASE`. Without this, a full table scan on the `players` table would be required.

### Match History for Rating History Chart

Query: "Get all rating snapshots for player P in season S, ordered by timestamp."

`idx_rating_snapshots_player_season_time` covers `(player_id, season_id, timestamp)` — a direct B-tree range scan for the entire chart dataset, ordered at the storage level.

## Foreign Key Cascade Behaviors

| Relationship | ON DELETE |
|--------------|-----------|
| login_attempts → users | CASCADE (user deleted = attempts deleted) |
| league_operators → leagues | CASCADE |
| league_operators → users | CASCADE |
| seasons → leagues | CASCADE |
| league_players → leagues | CASCADE |
| league_players → players | CASCADE |
| invite_tokens → players | CASCADE |
| match_participants → matches | CASCADE |
| match_audit_log → matches | CASCADE |
| rating_snapshots → matches | CASCADE |
| recalculation_jobs → seasons | CASCADE |
| matches → seasons | RESTRICT (matches must be deleted before season) |
| match_participants → players | RESTRICT (player with matches cannot be hard-deleted) |
| rating_snapshots → players | RESTRICT |
| rating_snapshots → seasons | RESTRICT |

RESTRICT on match participant and rating snapshot relationships enforces that player hard-deletion is blocked if the player has match history. Soft-delete via `league_players.is_active = 0` is used instead.

## WAL Mode Concurrency Model

SQLite in WAL mode supports:
- **Multiple concurrent readers.** Read transactions do not block each other or writers.
- **One concurrent writer.** Write transactions queue behind each other.
- **Readers do not block writers.** Writers do not block readers (readers see the last committed snapshot).

This model supports the two-process access pattern (Axum backend + Swarm Operator process) without a broker:

- Swarm writes (match recording via library): one write at a time, serialized at SQLite level
- Backend reads (leaderboard, dashboard): concurrent, not blocked by swarm writes
- Backend writes (match corrections, season management): queued behind swarm writes if concurrent

`busy_timeout = 5000ms` means a write that cannot acquire the write lock immediately will retry for up to 5 seconds before returning `SQLITE_BUSY`. This is appropriate for the expected write concurrency (not designed for thousands of concurrent writers).

# ADR-0008: Invite-Gated Registration with Open-Registration Pivot Path

**Status:** Accepted
**Date:** 2026-04-17
**Deciders:** Dustin Kerns

---

## Context

The platform requires user accounts for authentication and RBAC. The question is how new user accounts are created:

1. **Open registration** — any visitor can self-register with username, email, and password.
2. **Admin-only creation** — no public register endpoint; Admin sets temporary passwords for each new user.
3. **Invite-gated registration** — a one-time invite token (generated by Admin or League Operator for a player record) is required to register. The token creation and account creation are atomic.

The product already specifies invite tokens for player-to-account *linking* (SR-AUTH-005). The question is whether these tokens also gate the creation of the `users` row.

An additional constraint: the future option to move to open self-registration must not require architectural surgery.

---

## Decision

`POST /api/auth/register` requires a valid invite token in v1.

The request body is: `{ username, email, password, invite_token }`.

The handler:
1. Validates the token (not expired, not already claimed) via Auth Repository
2. Creates the user account
3. Claims the token (links the new `user_id` to the `player_id` the token was issued for)

Steps 2 and 3 execute within a single SQLite transaction. Either both succeed or neither does.

The `POST /api/auth/invites/{token}/claim` endpoint is **retained** for already-authenticated users who receive an invite link after they have an account. Both flows share the same token validation logic in the Auth Repository.

### Pivot path to open registration (Option A)

The token requirement is enforced by a single server-side validation check, not by architectural structure. To allow open self-registration in a future version:

1. Make `invite_token` optional in the request body (schema change: `String` → `Option<String>`)
2. Skip token validation when absent
3. Skip the player-link step when no token is provided (account is created unlinked)

No endpoint changes, no schema migrations, no client changes are required. The pivot is a one-file server-side change.

---

## Rationale

### Invite-gated is appropriate for v1

The platform is single-tenant and internally operated. Uncontrolled self-registration would allow anyone with the URL to create an account. Because there is no email verification infrastructure in v1, there is no mechanism to confirm a registrant's identity. Requiring an invite token ensures that every account is tied to a known player record from the start.

### Preserving the pivot path

The pivot to open registration is explicitly preserved because the platform may evolve toward self-service — where players discover the platform and create accounts independently before being added to a league. Architectural choices that would make this expensive (e.g., baking invite validation deep into the data model or eliminating the register endpoint entirely) are avoided.

### Single-step register + link

Requiring the user to register and then separately claim a token is unnecessary friction. The invite URL should take the player to a single registration page that completes both actions. This matches the user journey in `docs/specs/user-journeys.md`.

---

## Alternatives Considered

### Open registration (Option A) in v1

Rejected for v1. Without email verification, open registration allows arbitrary account creation on an internal platform. The invite token adds a meaningful access gate with minimal UX friction. Option A is preserved as a future path, not rejected permanently.

### Admin-only creation (Option B)

Rejected. Requires the Admin to create every account, which does not scale even for a small organization. The UX burden is higher than the security benefit over invite-gating.

---

## Consequences

### Positive

- Every user account in v1 is linked to a known player record from registration
- No email infrastructure required
- The platform's self-registration path is preserved for future activation
- Both registration paths (new user + invite, existing user + claim) share token validation logic in the Auth Repository

### Negative / Accepted Trade-offs

- An Admin or League Operator must generate an invite token before a player can register. There is no self-service account creation without an invite.
- If an invite token expires (7-day window) before the player registers, a new token must be issued.
